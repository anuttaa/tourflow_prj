# TourFlow — информационная система формирования туров

Курсовая работа по дисциплине «Интегрированные информационные системы и компоненты» (БГУИР).
Тема: **информационная система оптимизации процессов формирования туров с алгоритмом автоподбора альтернативных опций и валидацией временных графиков.**
Реализация соответствует ТЗ (документ «ТЗ: ИС формирования туров»), этап **[КР]**; архитектура рассчитана на расширение до дипломного проекта.

## Состав

| Компонент | Порт (внутри сети) | Назначение |
| --- | --- | --- |
| `frontend` (React + TypeScript + Vite, Nginx) | 443 → хост 8443 (HTTPS), 80 → 8088 | Веб-интерфейс, TLS на границе, проксирует `/api` в gateway |
| `services/gateway` (Spring Cloud Gateway) | 8080 | Единая точка входа: JWT, роли, CORS, лимит запросов, маршрутизация |
| `services/identity-service` | 8081 | Регистрация, подтверждение email, вход, JWT RS256 (JWKS), роли, профили, аудит |
| `services/catalog-service` | 8082 | Направления, поставщики, опции, календарь квот, удержание мест, кандидаты для автоподбора |
| `services/planning-service` | 8083 | **Ядро:** туры, версии, сегменты, валидация графика (VR-01…VR-10), автоподбор, цена, публикация, отчёты |
| `services/booking-service` | 8084 | Заявки, hold + компенсация, машина состояний, штрафы, оплата (sandbox), отчёты |
| `services/notification-service` | 8085 | Потребитель событий Kafka, письма (SMTP), журнал отправок |
| PostgreSQL 17 | 5432 | Отдельная БД и пользователь на каждый сервис (database-per-service) |
| Apache Kafka 3.9 (KRaft) | 9092 | События через transactional outbox |
| MailHog | 8025 (хост) | Перехват писем в демо-окружении |

Внешний API — REST (OpenAPI/springdoc), межсервисные вызовы — REST с сервисным токеном (`/internal/**`, наружу не публикуются) и Kafka. GraphQL/gRPC в КР не используются (обоснование — раздел 8.1 ТЗ).

## Быстрый запуск (Docker)

Требуется Docker с Compose v2, не менее 8 ГБ ОЗУ.

```bash
cp .env.example .env          # задайте свои пароли и INTERNAL_TOKEN
docker compose up -d --build  # первая сборка занимает несколько минут
```

* Веб-интерфейс: <https://localhost:8443> (самоподписанный сертификат — подтвердите исключение в браузере)
* Письма (подтверждение email и уведомления): <http://localhost:8025>
* Отладка с открытыми портами и Swagger UI сервисов: `docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d`, затем `http://localhost:8081..8084/swagger-ui.html`
* Остановка: `docker compose down`; с удалением данных: `docker compose down -v`

Миграции Flyway и демо-каталог (3 направления, ~60 опций, квоты на даты через 3 недели от запуска) применяются автоматически. Данные хранятся в томе `pgdata`.

## Демонстрация сквозного сценария (UC-04 → UC-05 → UC-06 → UC-07)

1. Войдите как **manager** → «Конструктор» → **«Создать демо-туры»**. Появятся два тура: корректный и с намеренными конфликтами.
2. Откройте тур «…с конфликтами»: на временной шкале красным подсвечены сегменты, ниже список конфликтов (VR-01 наложение экскурсий, VR-02 короткая стыковка после прилёта, VR-05 экскурсия до открытия, VR-06 ранний заезд, VR-07 непокрытая ночь, VR-02 перед вылетом).
3. Выберите сегмент → **«Подобрать замену»**: система возвращает top-N альтернатив с оценкой, вкладом критериев и пояснением; **«Применить»** выполняет подстановку и каскадную перевалидацию.
4. Исправьте остальные конфликты (кнопки сдвига времени, удаление/добавление сегментов из каталога) и нажмите **«Опубликовать»** (публикация блокируется при ошибках, при недоступности каталога и пишет событие в Kafka).
5. Как **client** откройте витрину → тур → оформите заявку (места удерживаются на 30 минут). Как **manager** подтвердите заявку в «Очереди заявок». Клиент оплачивает (sandbox) или отменяет; письма видны в MailHog.
6. «Отчёты» (manager/admin) и «Администрирование» (admin: пользователи, правила VR с редактированием параметров, журнал аудита).

## Алгоритмы (раздел 7 ТЗ)

* **Алгоритм 1, валидация графика** — `services/planning-service/.../engine/ScheduleValidator.java`: чистая функция без зависимостей от Spring, правила VR-01…VR-10 и BR-01, граф стыковок с запасом (slack), параметры из таблицы `validation_rules`.
* **Алгоритм 2, автоподбор** — `.../engine/AlternativeEngine.java` + `AlternativeService`: кандидаты из каталога → жёсткие ограничения (прогон валидатора с подстановкой, бюджет) → нормировка → `S(c)=Σ wᵢ·fᵢ(c)` → top-N с объяснением; применение в одной транзакции, при новых ошибках решение фиксируется как REJECTED в отдельной транзакции.
* **Алгоритм 3, бронирование** — `booking-service/BookingService`: hold в catalog (атомарный `UPDATE … WHERE quota_free >= :q`), сохранение заявки и события в одной транзакции (outbox), компенсация (`release`) при сбое, TTL и автозакрытие.

## Безопасность

HTTPS на Nginx (TLS 1.2/1.3, заголовки CSP, X-Frame-Options, nosniff); пароли — BCrypt; JWT RS256 (access 15 мин, refresh 7 дней с ротацией и отзывом, ключ в томе identity, остальные сервисы проверяют по JWKS); RBAC на gateway и в сервисах + проверка принадлежности объекта; `/internal/**` только с сервисным токеном и не маршрутизируется gateway; лимит запросов на gateway; блокировка входа после 5 неудачных попыток; параметризованные запросы (JPA, JDBC); единый формат ошибок RFC 7807 без утечки деталей; секреты только из окружения (`.env`).

## Соответствие ТЗ

Реализованы **P0 и P1**: FR-01…FR-15, FR-17, FR-19…FR-21, FR-23…FR-27, а также FR-22 (оплата в режиме sandbox, без webhook) и FR-16 частично (версии: создание новой версии и API списка; интерфейса сравнения diff нет).
**Не реализовано** (P2 / [КР+] по ТЗ): FR-18 (шаблоны туров; таблица `tour_templates` создана миграцией), FR-28 (экспорт PDF/ICS).

Отличия от текста ТЗ, которые стоит указать в пояснительной записке:

* перемещение сегментов на шкале — через поля времени и кнопки сдвига, а не drag-and-drop; шкала написана без vis-timeline;
* валидация пересчитывается целиком (без инкрементального режима) — для туров до сотен сегментов это не критично;
* Redis, Prometheus/Grafana не включены (в ТЗ — [КР+]); метрики доступны через Actuator `/actuator/health`;
* секреты передаются через переменные окружения, не через Docker secrets;
* аудит (FR-27): события безопасности в `audit_log` identity + история статусов заявок и версии туров.

## Известные ограничения и дальнейшая проверка

Версии: Java 21, Spring Boot 3.5.6, Spring Cloud 2025.0.0, PostgreSQL 17, Kafka 3.9, React 18, Vite 5 — зафиксируйте фактические версии в ПЗ (п. 3.3.2 бланка) после первой успешной сборки.
Код писался без доступа к сети: алгоритмы и тесты движка проверены локально, Java-код сервисов проверен только на синтаксис, фронтенд собирается esbuild'ом и проходит проверку типов на заглушках React. **Первая сборка `mvn verify` и `docker compose up --build` может потребовать мелких правок**; при ошибках компиляции присылайте вывод — исправлю.
